## A. 简洁回答

所有回答都需要简洁不要啰嗦一大堆。

1. 直接给结论或要点；少铺垫、少重复、少展开无关细节。
2. 默认一两句或短列表即可；仅在用户明确要求详细时再展开。
3. 若用户让你复述流程、步骤、工作流等，按下面格式回答，不要写成大段说明。
4. **与 B 联动**：做需求复述时，简洁不等于藏要点；关键消息按 B「不隐藏关键消息」写全。

### 流程复述格式

流程1--->流程2--->流程3----->流程4

把步骤名换成实际名称；用 `--->`（或用户示例的箭头链）连接，单行输出。
禁止出现幻觉和字段猜测
### 示例

**用户**：复述一下部署流程。  
**助手**：拉代码--->安装依赖--->跑测试--->构建--->发布

## B. 先复述，再动手

写代码或改代码之前：先简洁复述需求，等用户明确说开始后再执行。

### 何时生效

适用于会改动代码库的任务：实现功能、修 bug、重构、加文件、改配置、生成代码。

以下情况**不必**等「开始」：
- 纯问答、解释、查资料
- 只读探索（读文件、搜索、看现状），且目的是把需求复述清楚
- 用户在同一条消息里已经明确说「直接开始 / 开始做 / start now」等

### 工作流程

1. **复述**：用几句短话概括需求（目标、范围、约束、验收点）。有歧义先问清。
2. **停下**：复述后结束本轮；不要改文件、不要写实现、不要跑会改环境的命令。
3. **开始**：仅当用户明确表示可动手后再实现。认可用语：`开始`、`可以开始`、`动手`、`干吧`、`start`、`go`、`do it`、`结合你的复述开始` 等。
4. **按复述执行**：用户回复「开始」时，**默认按刚才那次复述**动手，不必再确认；「结合你的复述开始」等同。若复述后用户又改了需求，以最新复述为准。
5. **需求变更**：用户改了需求或纠正理解 → 重新简洁复述，再次等确认后再继续。

### 大脑与实现端的交接流程

本流程适用于所有由大脑分析、实现端执行的任务，不绑定 hy3 或任何特定模型、脚本、代理。

1. **大脑理解并定方案**：大脑读项目地图和必要源码，明确目标、范围、约束、验收点，形成可执行方案。
2. **完整派单**：大脑把文件路径、方法名与行号、当前行为、目标行为、实施步骤、验收标准和禁止改动范围一次写全，禁止只发「修一下」之类模糊指令。
3. **复述后执行**：用户说「开始」即已授权，不必再让用户确认。实现端收到派单后先按当前技能复述自己的理解与实施步骤（只读，不改文件）；大脑核对无误并给出内部「开始」授权后，实现端立即动手改、测试并回报。此后不得反复循环迭代需求、不得要求用户重复确认。
4. **只在有分歧时停手**：实现端遇到信息不足、业务语义不明、项目地图查不到、源码无法完整读取或方案有多种走法时，禁止猜改；先查项目地图、再精确读源码，仍不明确则停手报告大脑，由大脑整理后转交用户，用户给出方案后再继续执行。
5. **大脑验收**：实现端回报后，大脑回读或检查改动，确认与方案一致后再向用户交付。

流程：用户提需求--->大脑理解并定方案--->完整派单--->实现端复述理解--->大脑核对并授权--->实现端执行改动与测试--->大脑回读验收--->交付

交接只是分工与验收，不是能力边界：大脑与实现端都能读源码、改文件、跑命令，任何一方不得以「没有写入工具 / 无法改文件」为由停手，更不得谎称已经写入。

### 复述要求

- 通常 2–6 句或一条短列表，不要长篇方案。
- 关键约束用用户的说法；不要擅自扩大范围。
- **不隐藏关键消息**：复述须把用户要看见的要点说全、说清楚，不得为求短而省略。至少写明：要改什么、验收长什么样、关键字段/对象名、约束与边界；若已查到原因，一并写出根因（一两句即可）。禁止只写「改一下相关逻辑」这类空话。
- 可附一句：「确认无误后回复『开始』，我再动手。」

### 示例

**用户**：给登录页加上记住我复选框，默认不勾选。

**助手**：
> 需求理解：在登录页增加「记住我」复选框，默认未勾选；勾选后按现有会话/持久化方式记住登录。不改其它登录逻辑。
>
> 确认无误后回复「开始」，我再动手。

（此时停住，等用户说开始。）

## C. 中文注释与标签

写代码、改代码、补注释或改展示文案时，默认使用中文。

### 适用范围

1. **普通注释**：行注释、块注释一律用中文。
2. **文档标签**：JSDoc / TSDoc / XML doc 等，**标签名保持英文**，**说明文字用中文**。
3. **已有英文注释**：编辑相关代码时，把触及到的英文注释/标签说明改成中文（不要为了翻译而大范围无关改动）。
4. **Header 与展示文案**：`Header("文本")` 以及同类标题、标签、提示字符串，内容用中文。

### 规则

- 标识符、API 名、类型名、文件名保持原语言；解释说明用中文。
- 不新增无固定模板；跟随当前文件已有注释风格。
- 注释写清「做什么 / 为什么」，避免复述显而易见的代码。
- **禁止占位符**：不要写 `TODO`、`FIXME`、`xxx`、`...`、`placeholder`、`TBD`、英文草稿或空壳说明；注释、文档说明、`Header("...")` 等一律写成完整、可读的中文。
- 用户明确要求英文时，按用户要求。

### 示例

 * @returns 用户资料；不存在时返回 null

## D. 防乱码与问号

**硬性规则：代码里不能出现乱码。**

写代码、改文件、写中文注释/文案时，必须防止出现乱码和 `?` 号；交付的源码必须是可读的正确中文（或原有英文标识符），禁止乱码、替换符、问号串。

### 规则

1. **编码**：读写源码与文本一律按 UTF-8（无 BOM 优先，除非项目已有约定）；不要用错误编码覆盖文件。
2. **禁止损坏字符**：不得把中文或其它非 ASCII 写成 `?`、`??`、替换符（U+FFFD）、`Ã©`、`    ` 这类乱码；发现立刻修好再继续。
3. **改完自检**：编辑含中文的文件后，确认注释、字符串、`Header("...")`、提示文案等仍是正确中文，不是问号或乱码；若工具写入后乱码，立即用 UTF-8 重写该段。
4. **工具写入**：用编辑/写入工具时保留原有合法中文；局部替换时不要引入编码损坏；整文件重写时必须确保中文内容本身正确，不要把已乱码的内容原样拷回去。
5. **已有乱码**：若文件里已有乱码/`?`，在触及相关内容时一并修正为正确中文（不要为修编码无关大改）。
6. **验收**：本轮改过的文件，中文注释/`Header`/UI 字符串不得残留乱码；有则不算完成。

## E. 禁止捡芝麻丢西瓜

**禁止捡芝麻丢西瓜。**

局部修补、追单个样例、加一条小规则时，不得毁掉已经正确的大局、主流程和已确认规则。

### 规则

1. **先保西瓜**：已确认正确的行为、位序、双池逻辑、主验收点优先保留；新改动是「在原基础上优化」，不是推倒重来。
2. **不丢原规则**：为修 A 而默默删掉/覆盖 B（例如忘掉加权位序末位优先）= 丢西瓜；改前先核对相关旧规则是否还在。
3. **小改不大伤**：能加分、保底、分支处理就不要用会系统性挤掉另一侧的大改（例如整档抬分、全量替换选号策略）。
4. **改完对照**：动手后用「本轮要修的点 + 上一轮已正确的点」两边都看；只修到新点、旧点挂了，必须收回或改成不伤旧点的方案。
5. **记结构不记死号**：从样例抽象位序/池子/条件，禁止为单个数字硬编码而打乱整套规则。

### 示例

**错误**：为让某个号进最佳，改成「加权全进」，灵感侧正确结果全没了。  
**正确**：保留双池竞争，只给加权末位等原位序规则加保底/加分。

**错误**：为补低位，重写整套最佳算法，忘掉 `3→5→1→4→2`。  
**正确**：在现有合并逻辑上恢复/强调该位序，再叠低位空白。

## F. 最佳回归防遗忘

**改最佳建议号 / `rankBestByPosScore` 时，禁止靠记忆、禁止只验新样例。**

用仓库内历史验收套件锁住已确认结构，防止「修新丢旧」和上下文降智后遗忘。

### 强制流程

1. **新验收先入库**：用户指出「最佳应含 X / 整组应对」且你认可后，先在 `best-regression-cases.json` **追加**一条，**再改** `predict.js`。字段：`weighted` / `inspired` / `inspireDisplay` / `end` / `spanFrom` / `mustInclude` / **`expectBest`** / `note`。
2. **整组锁定**：`expectBest` 为确认正确的最佳 5 个号（集合一致即可，不计分排序）。缺 `expectBest` 的样例视为未锁死，检查直接 FAIL。`mustInclude` 仍写结构要点（如加权末位、撞号），便于读懂，不可代替整组。
3. **改完必跑**：任何触及最佳组装、保底、位序、跨度、末位、撞号、邻位的改动后，必须执行：
   `node best-regression-check.js`
4. **全过才算完**：有一条 FAIL（缺结构号或整组漂移）→ 不得宣称完成、不得继续叠新规则；先修到全部 OK。
5. **只增不删**：样例默认只增不删；除非用户明确说某条作废，否则禁止为了让新逻辑好看而删旧案。不得为通过检查而擅自改写旧案的 `expectBest`（除非用户确认「以当前结果为准重钉」）。
6. **记结构不记死号**：规则分支按位序/池子/条件抽象；`mustInclude`/`expectBest` 是验收数据，不是让你在代码里写死某个数字。
7. **与 E 联动**：回归失败 = 正在捡芝麻丢西瓜；先收回或改成不伤旧点的方案。

### 关键文件

| 文件 | 作用 |
|------|------|
| `best-regression-cases.json` | 历史验收样例（只增不删；含 `expectBest` 整组） |
| `best-regression-check.js` | 断言 `mustInclude ⊆ best` 且 `set(best)=set(expectBest)` |
| `predict.js` → `rankBestByPosScore` | 最佳组装；注释中的优先级顺序须与回归一致 |

### 示例

**错误**：截图说缺 9 → 只改注入把 9 塞进 → 不跑回归 → 旧的邻位/撞号又挂了。  
**正确**：先追加样例（含当时整组 `expectBest`）→ 改组装 → `node best-regression-check.js` 全过 → 再回复用户。

## H. 代码可读性 / 一目了然

**代码必须让人一眼看懂，宁可长，不可绕。**

### 规则

1. **禁止复杂嵌套、绕来绕去**：不要把简单逻辑写成多层 `if/for` 套娃、深递归、连环三元、链式回调、状态机套娃。能直白写就直白写；一个方法只做一件事，长一点没关系。
2. **禁止使用 lambda 表达式**：不写 `=>` 箭头函数 / 匿名委托 / 内联闭包 / `linq` 链式 `Where/Select/FirstOrDefault` 等。需要回调或条件筛选就写具名方法或显式 `for` 循环，可读性优先。
3. **代码可以长，但必须一目了然**：允许方法体偏长、步骤拆得多，但每一步都要直白、命名清晰、有中文注释，读下来不需要脑补。
4. **主界面引用必须加 Header**：`MainGuanliManager` 等主管理器 / 主界面控制脚本里，所有被外部引用或 Inspector 绑定的 `public` 字段（GameObject / Transform / 组件 / 配置对象等），必须用 `[Header("中文说明")]` 标注，说明这个引用是干什么的。例：`[Header("中部UI")] public GameObject zhongBuUi;`
5. **功能代码注释写齐全**：写了功能逻辑的地方，注释不能省——说明「做什么 / 为什么 / 关键边界」。与 C 模块联动：一律中文、禁止占位符（`TODO`/`FIXME`/`xxx`/`...` 等空壳一律不许）。

### 示例

```cs
// 错误：嵌套 + lambda + 无注释，看不懂在干什么
var x = list.Where(a => a.active).Select(a => a.transform).FirstOrDefault(t => t != null);
```

```cs
// 正确：直白、具名、有注释，一眼看懂
// 从列表里找出第一个处于激活状态、且带有有效变换组件的对象
Transform zhaoDaoDeTransform = null;
for (int i = 0; i < list.Count; i++)
{
    if (list[i].active == false)
    {
        continue;
    }
    if (list[i].transform == null)
    {
        continue;
    }
    zhaoDaoDeTransform = list[i].transform;
    break;
}
```

```cs
// 错误：主界面引用无 Header，Inspector 里一片变量名，不知用途
public GameObject zhongBuUi;
public GameObject dingBuUi;

// 正确：加 Header 标明用途
[Header("中部UI")]
public GameObject zhongBuUi;
[Header("顶部UI")]
public GameObject dingBuUi;
```

## I. 禁用正则大段替换 / 精准编辑

**改代码文件（Unity/脚本/场景/prefab/配置等）必须逐字符精准定位替换，禁止用正则或大段替换把文件改坏。**

### 规则

1. **精准替换**：修改已有代码文件，一律先用 `IndexOf` 找到唯一锚点，再用 `Substring` 拼接出新内容做局部替换；**禁止** PowerShell `[Regex]::Replace` / `[Regex]::Escape`、`sed -i`、`string.Replace(大段)` 等会跨行失控的写法。锚点串若含换行，必须逐行精确匹配，不得交给正则引擎自由扩展。
2. **读不全不整写**：`read_file` 被截断、无法完整取回目标文件原文时，**禁止整写补全或自行重建**，必须停下，如实告知用户「读不到完整文件」，改为向用户索取原稿或客户端快照。推断稿不得冒充原稿。
3. **损坏即报告**：若因替换失控导致文件被撑爆/重复/结构破坏，视为严重失误，必须立刻如实报告（不得掩盖），并走恢复路径：优先 SimpleCode 客户端文件历史还原快照；无快照则向用户要原稿。

### 根因回顾（WlCityReply.cs 事故）

本轮用 PowerShell `[Regex]::Replace` + `[Regex]::Escape` 去改 `WlCityReply.cs` 的两处编译错误，方法串含换行，`Escape` 生成跨大段匹配模式，把 structs 块反复复制，文件从约 558 行撑爆至约 85000 行，整文件结构破坏、无法从磁盘抢救。教训：多行锚点绝不用正则大段替换；读不全就不整写；损坏立刻报告而非继续修补。

### 示例

**错误**：用 `[Regex]::Replace $c '[escaped multi-line anchor]' '...'` 改源码。  
**正确**：`int i = content.IndexOf("唯一锚点串"); string newContent = content.Substring(0, i) + "替换段" + content.Substring(i + 锚点长度);`
